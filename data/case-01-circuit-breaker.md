# 案例 1：TCP 熔断器 — 从"每 14 分钟人工重启"到"2.8h 内 12 次自愈"

## 问题背景

**现象**：ESP32 设备与树莓派 Hub 的 TCP 连接频繁中断后无法自动恢复，必须手动重启设备才能恢复通信。（人工真机实测才试出）

**影响**：用户每 14 分钟需要人工干预一次，设备完全无法无人值守运行。

**定位手法（人工设计的三段反证测试 —— 把"是否必须重启"变成唯一变量）**：

| 步 | 操作 | 结果 |
|---|---|---|
| ① | 关掉 Pi 侧的 Flask | 企微失效（预期）；**Web 端完全正常**（取数 + 显示控制）✅ |
| ② | **重新开启** Flask，**全程不碰 ESP32** | Web 端仍正常，**但数据不恢复** ❌ |
| ③ | 手动重启 ESP32 | 全部恢复正常 |

⇒ **这一步的价值：把"网络不稳"这个解释直接排除掉** —— 第 ② 步里**两头都是活的**（Pi 的 Flask 已重开，ESP32 的 Web 端正常），
数据却只在重启后才回来 ⇒ 卡点在**设备自己的状态机**里，不在链路上。**测试设计先于根因分析，方向在动手之前就定住了。**

## 根因分析

### 发现过程

1. **代码审查**（AI 查代码定位，在人工定好方向之后）：发现 `piHubOffline` 标志位置位后没有清除路径
2. **关键证据**：成功分支的 `piHubOffline = false` 是死代码，被同一标志守卫的块所包裹

```cpp
// 伪代码示意（结构与真实代码一致）
bool fetchQuoteFromPi(...) {
  if (!usePiHub || piHubOffline) return false;   // ← 一旦 offline 就整段返回
  ...
  if (piHubOffline) {                            // ← 永远执行不到
    piHubOffline = false;                        //    清除路径 = 死代码
    Serial.println("[Pi] Hub 恢复在线");          //    这行从未打印过
  }
}
```

### 根因确认（**人工设立的硬性门槛：先查根因再定方向，所有项目通用⭐**）

> **一旦发现**：某个异常**只能靠"重启"复位**（重启就好、不重启就一直坏）
> **立刻判定**：这不是链路 / 环境问题，是**状态机的恢复路径缺失**
> **必须做**：找到那个标志位，**逐条列出它的置位路径与清除路径** —— 缺清除路径就是根因
> **不许做**：用"多试几次""换个网络再看看"绕过去

**熔断器缺少 HALF-OPEN 状态**：
- 连接失败 → 标记 `piHubOffline = true`
- 后续所有请求直接走兜底，不再尝试 Pi
- **没有探测恢复机制** → 单向闩锁，永不自愈

### AI 的失误（照实记）

- 熔断器只实现了 **CLOSED / OPEN 两态**，清除语句被写进了**永远执行不到的块**里（见上面那段伪代码）。
- 更值得记的是：它**从未被执行过，也从未被发现** —— `"[Pi] Hub 恢复在线"` 这行日志**一次都没打印过**。
  ⇒ **写下的代码从未被执行 ≠ 已测试通过**。三个 fetch 函数（Quote / Kline / Weather）是同一份模式，**一起哑**。

## 解决方案

### 修复策略

引入三态熔断器：CLOSED（正常）→ OPEN（熔断）→ HALF-OPEN（探测）→ CLOSED

**关键实现**：
- 每 60 秒放行一次探测请求
- 探测成功 → 立即恢复在线状态
- 探测失败 → 继续等待下一个 60s 窗口

```cpp
// 伪代码示意
if (piHubOffline) {
    unsigned long now = millis();
    if (now - lastProbeTime >= 60000) {  // HALF-OPEN 探测窗口
        lastProbeTime = now;
        allowProbe = true;  // 本次放行一次尝试
    }
}

if (!piHubOffline || allowProbe) {
    // 尝试 Pi 路径
    if (success) {
        piHubOffline = false;
        Serial.println("[Pi] Hub 恢复在线");  // ← 实测日志有此行
    } else if (allowProbe) {
        // 探测失败，继续等待
    }
}
```

## 验证结果

**判据（直接取自人工那三段测试的第 ② 步，是可直接在真机上复现的验收动作）**：

> **Pi 停掉再启动，全程不碰 ESP32 —— 数据必须自己回来。**
> ⇒ **验收动作里不许出现"重启 ESP32"** —— 修复前正是这一步在掩盖问题。

### 实测数据（2.8 小时长跑，日志：`logs/serial_20260913_213228.log`）

| 事件 | 次数 |
|------|------|
| `标记离线` | 14 次（**含重复打印，实际中断 12 次**） |
| **`Hub 恢复在线`** | **12 次** |
| `Quote OK` | 1,624 次 |
| `Quote 失败回退` | 166 次（失败率 9.3%） |

⇒ 12 次真实中断，**12 次全部由半开探测自动恢复**（两个数字的差来自重复打印，不是漏恢复）。

**跳闸时间线示例**（60s 探测节拍清晰可见）：
```
21:33:00 标记离线  →  21:34:04 Hub 恢复在线   (64s)
21:34:20 标记离线  →  21:35:26 标记离线       (66s，探测失败)
                   →  21:36:30 Hub 恢复在线   (64s，探测成功)
```

### 对比结论

| 维度 | 修复前 | 修复后 |
|------|--------|--------|
| **人工干预** | 每 14 分钟重启一次 | **零干预** |
| **自愈能力** | 无，永久失联 | 12/12 次自动恢复 |
| **最长失联** | 无限（直到人工重启） | 每 60 秒尝试一次恢复；实际失联时长取决于 Hub 何时恢复。 |
| **可用性** | 需要有人值守 | 可无人值守运行 |

## 关键洞察

1. **熔断器必须是三态的**：HALF-OPEN 不是可选优化，是自愈的必要条件
2. **清除语句写在被同一标志守卫的块里 = 死代码**：识别法仅需 3 秒
   > **一旦看到** `if (flag) { … flag = false; … }`，转头看它前面有没有 `if (flag) return;`
   > ⇒ **有，当场判死** —— 那行清除永远不会被执行
3. **自愈优于被通知**：设备主动探测恢复，不依赖外部信号

## 可复用模式

**熔断器标准实现清单（所有项目通用⭐）**：
- [ ] 开关状态（OPEN / CLOSED）
- [ ] 失败计数器
- [ ] 探测窗口定时器（HALF-OPEN）
- [ ] **关键**：恢复路径不能被开关本身守卫 —— 上面那行死代码就踩在这一条

**串口诊断注意事项（可复用⭐）**：
- ping 显示"0% 丢失"不代表网络真通（ARP 失败也计入已接收）
- 串口无限重复同一行 = 重试风暴
- 失败重试必须有退避，否则单核 C3 会失联

---

**这个修复的价值**：把"每 14 分钟人工干预一次"变成了"零干预"，是从"原型"到"可用产品"的关键里程碑。
