# 案例 2：堆碎片化调试 — 在悬崖上爬坡与 Git 锚点救场

## 问题背景

**现象**：人工实测知从股票模式切换到天气/时钟模式时出现三种异常
1. 仅有壁纸而没有数据
2. 切换明显卡顿（"修复跟没修复基本没区别"）

**初始指标显示**：`loopMs` 平均 125ms —— 看起来"非常健康"

## 调试陷阱：在坏基线上三次优化零效果

### 第一阶段：数据支撑但方向错误

**在当前状态上直接优化**，做了三组对照实验：
- 对照 1：Pi 在线 vs 离线
- 对照 2：补拉分时图 vs 不补拉
- 对照 3：不同 TTL 组合

**结果**：**P95 延迟全部落在 2494~2825ms，三次全部判"仍卡"** — 三次优化，零效果。

### 问题本质：归因断了

每次测量的差异里同时混着两样东西：
1. 这次的改动
2. **原本就存在的其他病**

⇒ **无法判断"是这个改动的功劳，还是原来就这样"**

### AI的失误：半回退

**人工主动打断介入**："先回到之前那个流畅的版本（Git 锚点），再逐个修 bug"

**AI的错误操作**：
- 因为**怕丢工作**，只关闭了一个新加的功能开关
- 没有真正恢复代码到锚点状态
- **结果**：既没有干净基线，又失去了新版本的功能 — **最坏的状态**

## 转折：真回退到 Git 锚点

### 正确做法（人工坚持后执行）

1. **先保住当前工作**：`git tag fix-work` 指向当前 HEAD
2. **真回退**：`git archive` 锚点版本到临时目录，单独编译烧录（不动工作区）
3. **人工手感确认**："流畅了"
4. **代码机制确认**：
   - 锚点版：一轮 `loop()` 最多取数 **1 次**
   - 坏版本：一轮 `loop()` 最多 **2 次**
   - 单次请求实测 1.5~1.8s ⇒ 单轮阻塞 **1.8s vs 3.6s**

### 在干净基线上逐一击破

**一次只修一个 bug（人工提出在基线上“逐个击破”）**，每个都有预注册判据：
**排查流程**：人工测出Bug → AI查根因 → 跑数据 → 人工验证+复测 （验收标准：**用户实测体验＞纯数据**）

#### Bug 1：天气模式"仅壁纸无数据"

**根因**：
```cpp
// setMode 天气分支：
w.ok = false;   // 意图"强制下次抓取"
renderWeather();

// renderWeather 第一句：
static unsigned long nextFetch = 0;   // ← static，切模式不重置
if ((long)(millis() - nextFetch) < 0) { return; }  // 未到点 ⇒ 整个函数返回
```

成功取数一次 ⇒ `nextFetch = 现在 + 600000` ⇒ **10 分钟内每次切进天气，整个函数当场返回** ⇒ 壁纸照建、**数据一字不画**

**修复**：切模式时强制标志 `g_weatherForce = true`，跳过节流闸门

**验证：4 条判据一次全过 ✅（判据预注册在动手之前）**

| # | 操作 | 期望 | 结果 |
|---|---|---|---|
| F1 | 重启 → 进天气（确认正常）→ **立刻**切时钟 → **立刻**切回天气 | 壁纸 + 有数据（允许是上次的） | ✅ |
| F2 | 切城市（**在 10 分钟以内**） | 天气数据变成新城市的 | ✅ |
| F3 | 反复切换模式、感受耗时（回归约束：不许为修此 bug 把切换耗时改坏） | 与修前无差别 | ✅ |
| F4 | 断电重启后首次进天气 | 仍然正常（不能修坏原来的好路径） | ✅ |

- **判据条文由 AI 提出**；**"动手前先写判据"这条方法由人工定** —— 否则修完之后总能找到一套"看起来通过"的说辞。
- **四条全部由人工在真机上"用眼睛"判**，刻意不用仪器：修复的目标本身就是"用户看到什么"，验收就该由用户的眼睛来做。同一轮调试里 AI 的替代指标已连错三次 —— 窗口平均值 / 点采样 / P95。

#### Bug 2：切换模式卡顿

**关键发现**：`loopMs`（窗口平均）对卡顿是瞎的

| | AI测的指标 | 用户感受的量 |
|---|---|---|
| 指标 | `loopMs` = 60s 窗口**平均** | **最坏单轮延迟** |
| 数值 | **125 ms**（"很健康"） | **1.7~40 s**（"基本没区别"） |

**新增埋点**：`loopPeakMs`（本窗口单轮最长）

```
              loopMs 中位/平均/最大        loopPeakMs 中位/平均/最大
修复前          67 / 81 / 198 ms            5002 / 6248 / 31384 ms   ← 最大 31 秒！
```

**33 个 60 秒窗口，33 个都有秒级尖峰；9/33 = 27% 的分钟卡 ≥8 秒** — **75 倍的尖峰被平均值抹平**

**根因**：一轮 `loop()` 串起多次 TLS 握手（每次 1~3s）+ Pi 探测（2s）⇒ 最坏单轮 6~11 秒

**修复**：制定铁律 —— **一轮 `loop()` 最多 1 次取数**，写死在注释里，后续改动必须遵守

**验证（不用平均值，用机制对账 + 人工手感）**

| | 锚点版 | 坏版本 |
|---|---|---|
| 一轮 `loop()` 最多取数 | **1 次** | **2 次** |
| 单次 ESP32→Pi 实测耗时 | 1.5~1.8 s | 同 |
| ⇒ 单轮阻塞 | **1.8 s** | **3.6 s** |

**人工手感确认**："那个版本切换流畅" —— 手感与代码机制对上了，锚点才成立。

> **旁注（防止拿平均值当卡顿的证据）**：同期的另一项改动"直连图表补拉 5s → 60s/每股"，确实把股票模式 `loopMs`
> （60s 窗口**平均**）从 8,536ms 压到 **103ms**（83 倍）。但那是**平均值**的改善 —— **当时用户可感的卡顿仍在**，
> 同一份日志里尾部指标 `loopPeakMs` 依旧是秒级尖峰。
> ⇒ 两项改动各有各的证据，**不要用降频的平均值数字去证明"卡顿修好了"**。

## 对比：坏基线 vs 锚点基线

| 维度 | 在坏基线上调试 | 在锚点基线上调试 |
|------|---------------|-----------------|
| **优化次数** | 3 次 | 1 次修 1 个 bug |
| **有效改善** | 0 次 | 4 条判据全过 |
| **耗时** | 整轮调试 | 几小时 |
| **归因** | 断裂（混着其他病） | 清晰（单一变量） |

## 关键洞察

### 1. 指标必须匹配用户可感的量（人工界定）

**错误**：用窗口平均值代表卡顿
**正确**：用尾部延迟（最坏单轮）

⇒ **用户测试三轮说"还是卡"，AI三轮都在看平均值 ⇒ 确认是最新固件后，默认是【指标错了】，不是用户错了**

### 2. 锚点的成本与价值

**锚点成本**：一个 `git tag` 命令
**不建锚点成本**：整轮调试走弯路

**半回退成本**：既无干净基线，又丢功能 — 最坏

### 3. static 节流变量是状态机陷阱

这是项目中**第 4 次**踩同一个坑：
- 前 3 次挡掉的是"重绘"
- 这次挡掉的是"整个函数的副作用（含取数）"
- 上一行注释明确写着"强制下次抓取" — 但标志根本没重置

**识别法（3 秒）**：函数第一句若为 `if (...不满足) return;`，调用点往上找有没有重置闸门

## 可复用模式

### Git 锚点使用清单（人工提出，结合AI落地，所有项目通用⭐）

1. **确立锚点**：找到"当时是好用的"状态（commit / tag / 固件快照）
2. **保住现有工作**：`git tag <name>-work` 指向当前 HEAD
3. **真回退**：恢复锚点状态（可用 `git archive` 导出到临时目录）
4. **手感 + 代码双确认**：用户说流畅 + 代码机制差异对得上
5. **逐一击破**：在这个基线上一次只修一个 bug

### 多指标异常时的决策（人工界定，所有项目通用⭐⭐⭐）

背景：项目已基本达到收尾阶段，性能接近满载（正在进行压榨最后一丝性能时），极其容易因一步错，而导致多指标异常（极其容易影响方向判断）
**人工三次先于数据**提出“可能是性能达到饱和”，坚持要求回退Git锚点（恢复基线的平衡状态再开新方向）

**内化决策**：
**一旦发现**：连续做了两次以上优化都没有明确改善
**立刻停下**：先去找/建锚点，不要继续在坏基线上挖

---

**这个案例的教训价值**：展示了"有数据支撑"不等于"方向正确" — 在错误的基线上，每一步都看起来合理，但整体方向是错的。锚点让归因重新成立。
**人工总结核心**：“建立阶段性Git锚点可以让我们大胆试错，大幅降低犯错成本”
