# 案例 3：上传非原子性 — 断电毁数据与备份恢复机制

## 问题背景

**现象**：网页上传壁纸/相册图片时，若在上传过程中断电或断网，设备重启后原图片被损坏，无法恢复。

**影响**：用户上传的图片可能永久丢失，且设备无法自动恢复到可用状态。

## 根因分析

### 原实现（非原子）

```cpp
// 伪代码示意
void handleUpload() {
    if (upload.status == UPLOAD_FILE_START) {
        targetFile = SPIFFS.open("/wallpaper.jpg", "w");  // ← 直接覆盖
    }
    else if (upload.status == UPLOAD_FILE_WRITE) {
        targetFile.write(upload.buf, upload.currentSize);
    }
    else if (upload.status == UPLOAD_FILE_END) {
        targetFile.close();
    }
}
```

**问题点**：
1. `UPLOAD_FILE_START` 就直接打开目标文件写入 → **立即覆盖旧数据**
2. 若中途断电，目标文件已被部分写入 → **既不是新文件，也不是旧文件**
3. 无备份、无恢复路径 → **数据永久损坏**

### 真机 A/B 实证

**实验设置**：
- 靶子文件：`/test.bin`（可逐字节读回验证，**不能用 jpg 当靶子**）
- A 组（修复前）：上传到一半拔电源
- B 组（修复后）：同样操作

**A 组结果**（修复前）：
```
上传前 sha256: 2914fa25...
中断上传
重启后 sha256: 025d5f3e...  ← 文件被毁
```

**B 组结果**（修复后）：
```
上传前 sha256: 2914fa25...
中断上传
重启后 sha256: 2914fa25...  ← 完全未变，旧数据完好
```

## 解决方案

### 修复策略：三阶段原子替换

```cpp
// 阶段 1: 写入临时文件
UPLOAD_FILE_START  → 创建 /tmp_upload
UPLOAD_FILE_WRITE  → 写入 /tmp_upload
UPLOAD_FILE_END    → 校验 sha256

// 阶段 2: 原子替换（关键）
目标文件 → .bak         // 备份旧数据
tmp_upload → 目标文件   // 新数据就位
删除 .bak               // 清理备份

// 阶段 3: 开机自动恢复
if (存在 .bak) {
    if (目标文件损坏或不存在) {
        .bak → 目标文件  // 恢复备份
    }
    删除 .bak
}
```

**关键设计点**：

1. **临时文件 → 校验 → 替换**：确保新数据完整后再动目标文件
2. **备份不能进开机删除名单**：`.bak` 是唯一留着旧数据的文件
3. **SPIFFS 的 rename 不覆盖**：已存在文件时 `rename()` 返回 false（实测确认）
4. **替换用三步**：`目标→.bak ⇒ tmp→目标 ⇒ 删.bak`

### 为什么不能用"失败就先删目标"

**错误方案**：
```cpp
if (rename(tmp, target) == false) {
    SPIFFS.remove(target);  // 删除旧文件
    rename(tmp, target);     // 再试一次
}
```

**问题**：删除旧文件 ⇒ 到 `rename` 成功之间存在**不可恢复窗口** — 断电后既无旧数据也无新数据

## 验证结果

### 断电边界测试

| 断电时刻 | 修复前 | 修复后 |
|---------|--------|--------|
| UPLOAD_FILE_START 之后 | 目标文件立即被毁 | 临时文件损坏，目标文件完好 |
| UPLOAD_FILE_WRITE 中途 | 目标文件部分损坏 | 临时文件部分写入，目标文件完好 |
| 阶段 2 第一步（目标→.bak）之后 | N/A（修复前无此步骤） | 有 .bak 备份，重启后自动恢复 |
| 阶段 2 第二步（tmp→目标）之后 | N/A | 新数据已就位，.bak 被清理 |

### 存储空间精确验证

**实测数据**：成功覆盖后存储精确回到 275 KB

**证明**：
- 备份文件（.bak）被创建
- 替换成功后备份被清理
- **没有残留垃圾文件**

### 恢复分支实测方法

**问题**：如何测试"开机自动恢复"这个分支？

**方法**：
1. 造出它依赖的状态：手动创建 `.bak` + 删除目标文件
2. 烧录固件到 app 分区（`esptool write_flash 0x10000 app.bin`）— **只烧 app 区，不格式化 SPIFFS**
3. 串口 + HTTP 双通道取证：
   - 串口看启动日志是否有 `[恢复] .bak → 目标文件`
   - `curl http://<IP>/list` 看文件列表（.bak 应消失）
4. 夹具必须零残渣：测完后删除所有测试文件

**实测结果**：✅ 恢复分支正常工作，.bak 被正确恢复并清理

## 关键洞察

### 1. ESP32 WebServer 上传语义

**易错点**：
- `upload.totalSize` 在 `UPLOAD_FILE_START` 时**必然为 0**（协议限制）
  - ⇒ 写在那里的限额判断是死代码
- 浏览器**不发**分段 Content-Length
- 客户端断开**会**回调 `UPLOAD_FILE_ABORTED`

### 2. 原子性的三个要素

1. **临时文件写入** — 不动目标文件
2. **校验完整性** — 确保新数据可用
3. **原子替换** — 备份 → 替换 → 清理，每步都可恢复

### 3. 无法自然触发的分支怎么测

**不能依赖**"等着它自然发生" — 恢复分支可能几个月都不触发

**主动造状态**：
- 用脚本/手动操作造出前置条件
- 正常启动一次
- 串口 + HTTP 双通道取证
- 清理测试痕迹

## 可复用模式

### 文件原子替换清单

```
□ 阶段 1: 写临时文件 + 校验
  □ 临时文件路径（如 /tmp_upload）
  □ 完整性校验（sha256 / 大小）
  □ 累计限额（可选）

□ 阶段 2: 原子替换
  □ 目标 → .bak（必须成功）
  □ tmp → 目标（必须成功）
  □ 删除 .bak（清理）
  □ .bak 绝不能进开机自动删除名单

□ 阶段 3: 开机恢复
  □ 检测 .bak 存在
  □ 目标文件损坏/不存在 → 从 .bak 恢复
  □ 清理 .bak

□ 错误处理
  □ UPLOAD_FILE_ABORTED → 删除 tmp，保留目标
  □ 替换失败 → 保留 .bak + tmp，记日志
```

### SPIFFS 文件系统注意事项

- `rename(src, dst)` 在 dst 已存在时**不覆盖**（返回 false）
- 必须先备份目标文件，不能依赖 rename 的覆盖行为
- 格式化参数 `formatOnFail` 要在初始化时设置

---

**这个修复的价值**：从"上传有风险"到"断电不丢数据" — 让设备从原型变成可靠产品。A/B 实证清晰展示了修复前后的差异，没有靠推理而是靠真实断电实验。
