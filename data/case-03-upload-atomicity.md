# 案例 3：上传非原子性 — 中断即毁旧数据，重构为可恢复的三阶段替换

## 问题背景

**现象**：网页上传壁纸/相册图片时，只要上传过程**被打断**（关掉页面 / 断网 / 掉电），设备上**原有的图片就已经被毁掉了**，无法恢复。

**影响**：用户已上传的图片可能永久丢失，且设备无法自动回到可用状态。

**要害**：旧数据的清除动作发生在**上传刚开始的那一刻**，而不是上传成功之后 ——
所以"没传完"这件事本身就等于"旧文件已经没了"，与传的是什么、传了多少都无关。

## 根因分析

### 原实现（非原子）

```cpp
// 伪代码示意
void handleUpload() {
    if (upload.status == UPLOAD_FILE_START) {
        targetFile = SPIFFS.open("/wallpaper.jpg", "w");  // ← 直接覆盖
    }
    else if (upload.status == UPLOAD_FILE_WRITE) {
        targetFile.write(upload.buf, upload.currentSize);
    }
    else if (upload.status == UPLOAD_FILE_END) {
        targetFile.close();
    }
}
```

**问题点**：
1. `UPLOAD_FILE_START` 就直接打开目标文件写入 → **立即覆盖旧数据**
2. 若中途中断（关页面 / 断网 / 掉电），目标文件已被部分写入 → **既不是新文件，也不是旧文件**
3. 无备份、无恢复路径 → **数据永久损坏**

### 真机 A/B 实证

**靶子（选靶标准，通用⭐）**：必须**能逐字节读回、且能逐字节还原**。

| 候选 | 判定 |
|---|---|
| `assets/city_data.json` → 设备上的 `/city_data.json` | ✅ **选它** —— 与仓库同名文件 sha256 相同 ⇒ 成功用例天然"设备不变"，可当场对账 |
| `1/2/3.jpg` | ❌ **绝不能当靶子** —— 设备上没有对应的下载路由，**坏了还原不回来** |
| `m.jpg` | ❌ 可读回，但那是使用者的背景图，不碰 |

**中断方式**：上传到一半**中止（客户端断开）**。

> ⚠️ **不是"拔电源"** —— 掉电本身没有复现，复现的是它留下的**状态**。见下方「能力边界」。

**A 组（修复前）**
```
上传前 sha256  2914fa25…   存储 275 KB
中断上传（连接断开）
读回   sha256  025d5f3e…   ← 文件被毁，存储掉 51 KB（写进去半截）
```

**B 组（修复后）**
```
上传前 sha256  2914fa25…   存储 275 KB
中断上传（连接断开）
读回   sha256  2914fa25…   ← 完全未变，旧数据完好；存储仍 275 KB
串口：上传中止: 连接断开（已收 N 字节），临时文件已丢弃；目标文件未改动
```

⇒ **同一支测试脚本、同一个靶子、同一种中断，唯一变量是固件** —— 这样的 A/B 才能结账。

## 解决方案

### 修复策略：三阶段原子替换

```cpp
// 阶段 1：收数据 —— 全程只写临时文件
UPLOAD_FILE_START  → 打开 /upload.tmp（先清掉上次残留）
UPLOAD_FILE_WRITE  → 边写边累计字节数；累计超过 512000 立刻中止并丢弃临时文件
UPLOAD_FILE_END    → 完整性校验：落盘字节数 == 收到字节数（**校验的是大小，不是 sha256**）

// 阶段 2：替换（三步，任何时候都不"先删目标"）
目标     → 目标.bak      // 先给旧数据留一份
/upload.tmp → 目标       // 新数据就位
删除 目标.bak            // 成功后才清备份
                         // 改名失败 ⇒ 立刻把 .bak 改回来（同步回滚）

// 阶段 3：开机认领（按目标名逐个查 .bak）
if (存在 目标.bak) {
    目标已存在 ⇒ 替换其实已完成、只是没来得及删备份 ⇒ 删掉多余的 .bak
    目标不存在 ⇒ 卡在中间那一步     ⇒ 把 .bak 改回原名（失败则打印"下次开机再试"并保留）
}
```

**关键设计点**：

1. **收数据阶段完全不碰目标文件** —— 传一半失败只是"这次没传进去"，设备上原有的东西毫发无损
2. **备份不能进开机删除名单** —— `.bak` 是唯一还留着旧数据的文件（代码里 `OLD_FILES` 故意不含 `.bak`）
3. **SPIFFS 的 rename 不覆盖**：目标已存在时 `rename()` 返回 false（实测确认）⇒ 必须先把目标改名为 `.bak`
4. **替换用三步**：`目标→.bak ⇒ tmp→目标 ⇒ 删.bak` —— 每一步之后断电，都还有可恢复的状态

### 能力边界（说清楚，不夸大）

| 边界 | 说明 |
|---|---|
| **是"尽力恢复"，不是"保证恢复"** | 回滚本身也失败时，设备打印"下次开机再试"并**保留 `.bak`** —— 不承诺一定能恢复 |
| **掉电本身没有复现** | 真机上造的是掉电**留下的状态**（目标缺失 + 有 `.bak`）⇒ 验证的是**恢复逻辑对不对**，不是"一定恢复得了" |
| **掉电对文件系统本身仍有损坏概率** | 这一层是应用层担保不了的 |
| **挂载失败会格式化** | 固件用 `SPIFFS.begin(true)`（挂载失败即自动格式化）—— 换来"存储坏了能自愈、不用接线救砖"，代价是**那种情况下所有文件都会没** |
| **替换时两个文件要同时占位** | 旧文件 + 临时文件并存 ⇒ 空间不足时上传会失败（**原有文件不受影响**）；控制台没有删除功能，只能用小图覆盖腾地方 |
| **并行/重入未防护** | 同时发起两个上传会共用同一个 `/upload.tmp` 与全局进度量。设备是单线程 HTTP，正常使用碰不到；**未实测，未防护**（不假装已覆盖） |

### AI 的失误（照实记）：把"失败"退化成"先删目标"

**AI 给出的方案**：
```cpp
if (rename(tmp, target) == false) {
    SPIFFS.remove(target);  // 删掉旧文件
    rename(tmp, target);     // 再试一次
}
```

**人工的介入**：**先判断失败根因，不要因为"偶然一次没成功"就把可能是唯一一份的目标数据删掉。**
**规则化（可复用⭐）**：凡 AI 提出的'先清理/先删除再重试'类方案，一律先问：这个清理动作本身会不会制造不可逆窗口

**根因**：删掉旧文件 ⇒ `rename` 成功之间是一个**不可恢复窗口** —— 正好卡在这里断电，**旧数据没了、新数据也没就位**。
⇒ 这与本次修复的初衷正好相反：本来是为了防丢数据，这个"补救"反而**新造了一个丢数据窗口**。

## 验证结果

**判据（三条，全部由真机实测判定 —— 不看日志自称）**

| # | 操作 | 期望 |
|---|---|---|
| C1 | 接收中途中断上传 | 目标文件 **sha256 不变** |
| C2 | 成功覆盖一次 | 存储**精确回到原值 275 KB** ⇒ 证明备份被创建**且被清干净**（若泄漏会多出约 58 KB） |
| C3 | 造出"卡在两步之间"的状态后开机 | `.bak` 被认领（该恢复的恢复、该清的清），内容与动手前**逐字节相同** |

### 中断点边界对照（逐个阶段）

| 中断时刻 | 修复前 | 修复后 |
|---------|--------|--------|
| 接收阶段（`FILE_START` 之后） | **目标文件当场被毁** | 临时文件损坏，**目标文件完好** |
| 接收阶段（`FILE_WRITE` 中途） | 目标文件部分损坏 | 临时文件部分写入，**目标文件完好** |
| 阶段 2 第一步（目标→.bak）之后 † | —（修复前无此步骤） | 有 `.bak` 在，**下次开机自动认领** |
| 阶段 2 第二步（tmp→目标）之后 † | — | 新数据已就位，多余的 `.bak` 被清掉 |

> † 这两行靠**造出该状态再开机**验证（掉电本身没有复现），方法见下。

### 存储空间精确验证

**实测数据**：成功覆盖后存储精确回到 275 KB

**证明**：
- 备份文件（`.bak`）被创建
- 替换成功后备份被清理
- **没有残留垃圾文件** —— 若备份泄漏，存储会多出约 58 KB

### 恢复分支实测方法（这条分支不可能自然触发）

**问题**：开机自动恢复这条分支，靠人为掉电也**测不出来** —— 掉电是否正好卡在两步之间不可控，
等它自然发生可能几个月都不触发。

**方法：造状态 + 正常启动一次**

1. **用临时夹具固件造出两种残留**（不靠碰运气掉电）：
   - 目标缺失 + 有 `.bak` ⇒ 期望"恢复"
   - 目标还在 + 有 `.bak` ⇒ 期望"清理多余备份"
2. **刷回正式固件**（`esptool write_flash 0x10000 app.bin`）—— **只烧 app 区、不格式化 SPIFFS**，
   这次启动就等于"下一次开机"。⚠️ 烧之前先把正在跑的固件本体整区读回存好，出问题能原样烧回。
3. **双通道取证**：
   - 串口看分支输出
   - **再用 HTTP 把文件读回来，与动手前的本地备份逐字节比对**
4. **夹具必须零残渣**：测完不留任何测试文件

**实测结果 ✅**

```
替换备份清理: /m.jpg.bak                                    ← 目标还在 ⇒ 删掉多余备份
上次替换中断，恢复 /city_data.json ← /city_data.json.bak (成功)  ← 目标缺失 ⇒ 恢复成功
删除无用文件: /test.jpg                                      ← 夹具标记被正式固件自动清掉（零残渣）
```

两个文件与动手前的本地备份**逐字节相同**，存储回到 275 KB。

⇒ **日志说"成功"不算数，必须再用一条可独立读回的通道（这里是 HTTP）比对字节。**

**踩到的坑**：夹具的"已跑过"标记**不能命名成开机清理名单里的名字**（如 `/test.jpg`）——
清理会把它删掉 ⇒ 下次启动又满足条件 ⇒ **无限重启循环**。
反过来，想让夹具"用完自动消失"，就用这种名字。

## 关键洞察

### 1. ESP32 WebServer 上传语义

**易错点**：
- `upload.totalSize` 在 `UPLOAD_FILE_START` 时**必然为 0**（核心在发出该状态**之前**就把它置 0 了，见 `Parsing.cpp`）
  - ⇒ **原来那句 `if (upload.totalSize > 512000)` 是死代码 —— 那个 500KB 限额从来没生效过**
    （不只是"检查得太早"）。改为**边收边累计**，用真实落盘量判定，与浏览器是否给出长度无关
- 浏览器**不发**分段 Content-Length
- 客户端断开**会**回调 `UPLOAD_FILE_ABORTED`（修复前这个分支根本不存在）

### 2. 原子性的三个要素

1. **临时文件写入** — 不动目标文件
2. **校验完整性** — 确保新数据可用
3. **原子替换** — 备份 → 替换 → 清理，每步都可恢复

### 3. 无法自然触发的分支怎么测（可复用⭐⭐）

**不能依赖**"等着它自然发生" —— 恢复分支可能几个月都不触发，靠碰运气掉电也复现不了。

**主动造状态**：
- 造出该分支**依赖的前置状态**（而不是去复现那个偶发事件本身）
- 正常启动一次
- **串口 + 可独立读回的通道（HTTP）双取证** —— 日志说"成功"不算数，要**比对字节**
- 清理测试痕迹，且**夹具的标记名不能与开机清理名单撞名**（会变成无限重启循环）

## 可复用模式

### 文件原子替换清单（所有项目通用⭐）

```
□ 阶段 1: 写临时文件 + 校验
  □ 临时文件路径（如 /upload.tmp）
  □ 完整性校验（本例：落盘字节数 == 收到字节数）
  □ 累计限额 —— 用"边收边累计"，不要用协议给的 totalSize

□ 阶段 2: 原子替换
  □ 目标 → .bak（必须成功）
  □ tmp → 目标（必须成功）
  □ 删除 .bak（清理）
  □ .bak 绝不能进开机自动删除名单
  □ 改名失败 ⇒ 立刻把 .bak 改回原名（同步回滚）

□ 阶段 3: 开机恢复
  □ 检测 .bak 存在
  □ 目标已存在 → 删掉多余备份；目标不存在 → 从 .bak 恢复
  □ 恢复失败 → 保留 .bak、打印原因、下次再试（**不承诺一定成功**）

□ 错误处理
  □ UPLOAD_FILE_ABORTED → 删除 tmp，保留目标
  □ 替换失败 → 保留 .bak + tmp，记日志

□ 说清边界
  □ 掉电对文件系统本身仍有损坏概率（应用层担保不了）
  □ 挂载失败自动格式化 = 那种情况下全丢
  □ 替换时旧文件与临时文件要同时占位
  □ 并行 / 重入是否已防护（本 case 未做）
```

### SPIFFS 文件系统注意事项

- `rename(src, dst)` 在 dst 已存在时**不覆盖**（返回 false）⇒ 必须先把目标改名为 `.bak`
- **挂载参数 `formatOnFail` 要显式决定**：本固件用的是 `SPIFFS.begin(true)`（挂载失败即自动格式化）——
  换来"存储坏了能自愈、不用接线救砖"，代价是**那种情况下所有文件都会没**。
  ⇒ 这是"讲安全"时最容易漏掉的一层：**应用层写对了、文件系统层做对了，挂载参数仍可能把数据全清掉**。

---

**这个修复的价值**：从"上传中途出任何意外就毁掉旧图"，到"接收阶段全程不碰目标文件、替换阶段可回滚、开机可认领" ——
而且把能力边界一并写清：**是"尽力恢复"，不是"保证恢复"**。
A/B 是真机上跑的（同一支脚本、同一个靶子、同一种中断，唯一变量是固件），不是靠推理。
