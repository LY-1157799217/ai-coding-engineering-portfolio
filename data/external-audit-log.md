# 外部复核记录 — 6 轮收敛过程

## 复核目标

发布前确保 README、代码注释、配置示例的准确性，避免"说了没做"或"做了说错"。

## 复核方法

1. **给源码不给结论**：让外部模型（GPT-4o）从头分析，不告诉它"我认为哪里有问题"
2. **要求指出行号**：避免泛泛而谈，每条缺陷必须定位到具体代码
3. **逐条回代码验真伪**：人工核实每一条，区分"确实错了"和"模型误报"
4. **迭代修复再复核**：修完一轮，再给它看，直到收敛

## 典型缺陷分类

### 类别 1：说了没做（最严重）

**示例 1**：README 宣称"设备会自动上报 IP"
- **查代码**：固件里没有调用 `/api/esp32_ip` 的逻辑
- **真相**：需要用户手动填一次
- **修复**：删除"自动"，改为"当前固件不会自动上报，必须手工填一次"

**示例 2**：文档说"所有埋点都记日志"
- **查代码**：`grep -n "帮助" app/wecom_bot.py` → `:374-379` 就地拦截，不走 MQTT
- **真相**：`帮助` 指令不进 devctl 的 `[ack]` 日志
- **修复**：教程改为"机器人会回 ≠ agent 收得到"，给出替代路径

### 类别 2：做了说错

**示例 3**：README 说"Flash 占用 95%，必须删 TLS"
- **查代码**：当前分区方案 `no_ota`，实际占用 62.2%
- **真相**：95% 是切分区方案前的过时数字
- **修复**：改为"62.2%，余量 774KB，无需删 TLS"

**示例 4**：注释说"formatOnFail 会自动格式化"
- **查代码**：这个参数在 `SPIFFS.begin()` 时设置，不是运行时行为
- **真相**：只有初始化失败时才格式化，不是"有问题就自动修"
- **修复**：补充"仅在挂载失败时"

### 类别 3：遗漏关键限定条件

**示例 5**：README 说"一律改成这个写法"
- **查代码**：有些是宏定义，不能乱改（编译会报错）
- **真相**：需要按值的类型分列（变量 vs 宏 vs 字面量）
- **修复**：补充"仅限运行时变量，宏值保持不变"

**示例 6**：文档说"安全存储"
- **查层次**：
  - 应用层：写入时校验 ✓
  - 文件系统层：原子替换 ✓
  - 挂载参数：`formatOnFail` **未设置** ✗
- **真相**：缺少底层保护
- **修复**：补充挂载参数配置

### 类别 4：跨文档不一致

**示例 7**：README 说"默认 60 秒"，但固件代码 `:343` 缺省是 5
- **查代码**：`prefs.getInt("refreshInterval", 5)` — 第二个参数是缺省值
- **真相**：全新设备（NVS 无该 key）实际跑 5 秒
- **修复**：要么改代码（5 → 60），要么改文档（承认真实行为）

### 类别 5：逻辑链条断裂

**示例 8**：文档说"会自动恢复"
- **查代码**：有 `if (fail) { ... }` 但**没有 else 分支**写恢复逻辑
- **真相**：失败后只是记日志，没有重试或恢复路径
- **修复**：删除"自动"，或者补上真正的恢复代码

**示例 9**：README 说"能处理 X/Y/Z 三种情况"
- **查代码**：`grep -n "种情况"` 只找到 X 和 Y 的处理
- **真相**：Z 没有对应代码
- **修复**：改为"当前实现处理 X 和 Y，Z 在路线图中"

## 自查清单（从 6 轮中提炼）

### #1 凡"所有/全部/N 个都…"，逐个数一遍
**陷阱**：`grep` 到"条件链相同" ≠ "分支体相同"
**方法**：手工展开每一个，确认行为一致

### #2 讲"安全"要把应用→文件系统→挂载参数每层过一遍
**陷阱**：应用层写对了，底层配置漏了（如 `formatOnFail`）
**方法**：从代码往下追到系统调用

### #3 "一律改成…"的照做型指令要按值的类型分列反例
**陷阱**：变量能改，宏值不能改（编译报错）
**方法**：区分 `#define` / `const` / 普通变量

### #4 写承诺要从代码的失败分支反推
**陷阱**："会/能/自动" → 先问有没有 else / 重试 / 恢复路径
**方法**：搜索 `if (fail)` 后面跟着什么

### #5 跨文档搬措辞 ≠ 通用
**陷阱**：A 文档说对了，复制到 B 文档就不对了（上下文不同）
**方法**：每个文档独立核查一遍

### #6 修"说反了"的说法要按"概念"搜，不要按"那句话"搜
**陷阱**：同一混淆可能散在多个文件
**方法**：搜关键词（如"自动"），不是搜整句

### #7 要扫**全部**文档
**陷阱**：只改了 README，INSTALL.md / FAQ.md 里还是老的
**方法**：`grep -r "错误说法" docs/`

### #8 缺陷成立 ≠ 归因成立
**陷阱**：外部模型说"是因为 X" → 真实原因可能是 Y
**方法**：只采纳"现象描述"，归因自己重新分析

### #9 保留不确定性要**整体重述**，不是在断言后加括号
**陷阱**："X 一定会发生（但也可能不发生）" → 自相矛盾
**方法**：改为"X 通常会发生，但在 Y 情况下可能不发生"

## 复核成本与收益

### 成本
- **6 轮调用**：每轮约 $X（token 量）
- **人工核实时间**：44 条 × 平均 5 分钟 = 约 3.7 小时
- **修复时间**：因缺陷而异，简单的几分钟，复杂的要改代码

### 收益
- **避免用户踩坑**：44 处不实宣称，每处都可能导致"照做不工作"
- **提升可信度**：README 承诺的都能验证
- **发现隐藏 bug**：第 3~6 轮发现的 7 条是我自己写错的代码逻辑

### ROI 判断
**值得**：对外发布的开源项目，README 是门面
**不值得**：内部原型、一次性脚本

## 关键发现

### 发现 1：第 3~6 轮全成立，且有 7 条是代码逻辑错误

**不是**只挑文档措辞，而是真的找到了代码 bug：
- 冷却判定顺序错了（应先于幂等）
- 被丢弃的指令不该登记（会导致重复炮）
- 恢复分支缺少前置检查

⇒ **外部复核的价值不仅是"说对"，还能找到"做错"**

### 发现 2：每轮都能挖出新问题，直到第 6 轮才真正收敛

**不能只做一轮**：
- 第 1 轮修完，代码变了，可能引入新问题
- 第 2~5 轮：前一轮修复暴露出新的不一致
- 第 6 轮：只剩措辞优化，可以结束了

### 发现 3："用户会照做的清单"必须回代码核

**最危险的地方**：教程里的操作步骤
- 用户会逐条执行
- 一步错，后面全错
- 必须在真机上走一遍，或者逐行对代码

## 可复用模式

### 何时启动外部复核

```
□ 对外发布前（开源项目 / 交付文档）
□ README 承诺了具体行为（"会自动…" / "支持 X/Y/Z"）
□ 有用户会照做的操作清单（安装 / 配置 / 排障）
□ 跨多个文档/仓库的一致性检查
```

### 何时不必做

```
□ 内部原型 / 一次性脚本
□ 代码注释（除非是 API 文档生成的源）
□ 临时调试日志
```
