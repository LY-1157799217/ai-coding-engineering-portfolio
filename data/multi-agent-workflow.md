# 人在环多 Agent 协同工作流

## 架构概览

**核心理念**：人负责判断与裁决，AI 负责执行与复核，通过接口契约与分阶段验收实现协同。

### 协同角色分工

| 角色 | 负责范围 | 典型任务 |
|------|---------|---------|
| **人（主导）** | 需求拆解、任务路由、冲突裁决、真机验收 | 定义"什么是对的"、最终验收 |
| **Claude Code** | Windows 侧固件开发、嵌入式调试 | ESP32 Arduino 代码、性能分析 |
| **OpenClaw** | Linux 侧服务开发、系统集成 | 树莓派 Python 服务、企微 Bot |
| **Work Buddy** | 低风险辅助任务 | 文档整理、数据提取 |
| **Codex / GPT-4** | 独立外部复核 | 发布前审查、缺陷发现 |

## 工作流程

### 阶段 1：需求拆解与任务路由

**输入**：用户需求（如"企微群里发指令控制设备"）

**人的决策**：
1. 拆解为子任务：企微 Bot（Pi 侧）+ HTTP 接口（ESP32 侧）+ MQTT 总线
2. 识别风险等级：企微凭证处理 = 高风险（人工审查）/ 网页按钮 = 低风险（AI 直接做）
3. 路由到合适的 Agent：
   - Pi 侧 Python → OpenClaw（Linux 环境）
   - ESP32 C++ → Claude Code（Windows + Arduino）
   - 两侧接口契约 → 人工定义后双方遵守

### 阶段 2：接口契约与协同边界

**契约内容**（ESP32 ↔ Pi 示例）：
```
GET /api/stock/{symbol}
- 响应体：扁平 JSON，< 4KB
- Connection: close（不用 chunked）
- 失败返回：HTTP 非 200，body 可为空
- 超时：ESP32 侧 2000ms
```

**关键约束**：
- 改动一侧需同步另一侧
- 契约由人审查，AI 不能单方面修改
- 跨系统集成点必须有人工验收

### 阶段 3：分阶段验收

**单侧验收**（各 Agent 独立完成）：
- Claude Code：ESP32 固件编译通过、串口日志正常
- OpenClaw：Python 服务启动、Flask 接口返回 200

**集成验收**（人工主导）：
- ESP32 能否从 Pi 拉到数据
- 企微指令能否到达设备
- **真机测试**：实际设备上操作，观察屏幕变化

**性能验收**（人工判断 + 量化数据）：
- 手感："切换卡不卡"（尾部延迟，不是平均值）
- 数据：12 小时长跑、堆内存趋势、崩溃计数

### 阶段 4：冲突裁决

**典型冲突场景**：

1. **AI 建议 A，数据显示 B**
   - 示例：AI 推理"堆碎片是 TLS 导致" → 实测降 TLS 3 倍，堆碎片不变
   - 裁决：**数据优先**，推翻 AI 假设

2. **两个 Agent 的方案冲突**
   - 示例：Claude Code 建议异步化，OpenClaw 建议降频率
   - 裁决：**评估风险与收益**，异步化未测过竞态 → 暂不做

3. **AI 说"已修复"，用户说"还是卡"**
   - 裁决：**默认是指标错了**，不是用户错了
   - 行动：换指标（平均值 → 尾部延迟）

## 成本控制与模型分级

### 模型选择策略

| 场景 | 模型 | 原因 |
|------|------|------|
| **主力开发** | Claude Opus/Sonnet | 长上下文、代码能力强 |
| **外部复核** | GPT-4o | 独立视角、挑错能力 |
| **批量处理** | DeepSeek/Qwen | 成本低、速度快 |
| **需求理解** | GPT-4（OpenClaw） | 企微自然语言解析 |

### 实际成本（两个项目周期）

**估算**（基于记忆中的使用量）：
- Claude Opus/Sonnet：主力开发 + 排查，约 $X/月
- GPT-4o：6 轮外部复核，约 $X
- DeepSeek/Qwen：数据处理 + 翻译，约 $X

**总计**：月均 $X（具体数字待补充）

### 成本优化策略

1. **复用上下文**：同一问题域的连续任务在同一会话
2. **分级处理**：简单任务用 Haiku，复杂推理用 Opus
3. **外部复核按需**：发布前才调用 GPT-4o，不是每次改动
4. **避免重复工作**：Git 锚点 + 增量修复，不推倒重来

## 关键协同模式

### 模式 1：跨系统协同（Windows ↔ Linux）

**场景**：ESP32（Windows 开发）需要与树莓派（Linux）集成

**协同机制**：
1. **人定义接口契约**：HTTP 路径、JSON 字段、超时策略
2. Claude Code 实现 ESP32 侧 HTTP 客户端
3. OpenClaw 实现 Pi 侧 Flask 服务端
4. **人工集成测试**：两侧代码都完成后，真机验证

**关键点**：
- 不让两个 Agent 直接通信
- 所有跨界面信息经人工转达
- 接口变更需人工同步通知两侧

### 模式 2：独立复核（外部模型）

**场景**：发布前确保 README、代码注释、配置示例的准确性

**复核流程**：
1. **给源码不给结论**：让 GPT-4o 从头分析
2. **要求指出行号**：避免泛泛而谈
3. **逐条回代码验真伪**：人工核实每一条
4. **多轮收敛**：18 → 9 → 7 → 4 → 4 → 2（累计 44 条）

**发现的典型错误**：
- "所有/全部/N 个都…" → 逐个数一遍（有例外）
- "安全" → 从应用到文件系统到挂载参数每层过一遍
- "一律改成…" → 按值的类型分列反例（宏值不能乱改）
- "会/能/自动" → 从失败分支反推（有 else 吗？）

### 模式 3：测量驱动迭代

**典型案例**：性能优化

1. **先测量建立基线**：12 小时长跑、堆内存趋势
2. **AI 提出假设**："TLS 慢是因为 X"
3. **设计可证伪实验**：改 X，预注册判据
4. **数据验证假设**：
   - 假设成立 → 归档，进入下一个
   - 假设证伪 → 推翻，换方向
5. **人工判定终点**："够用了" / "到边界了"

**关键原则**：
- **架构方向可假设，落地必须实测**
- 指标必须匹配用户可感的量（尾部 vs 平均）
- 小样本结论只能当假设，不能当数据

## 人机边界的核心原则

### 人负责的事（AI 不能代替）

1. **最终判断**："好不好用" — 手感是唯一判据
2. **风险决策**：删除 vs 保留、推送 vs 本地、异步化 vs 降频率
3. **优先级排序**：先修 A 还是先修 B
4. **验收标准**：什么叫"修好了"
5. **跨系统集成**：两侧代码都对，接口对不对得上

### AI 负责的事（人不必亲自做）

1. **代码生成**：根据需求写出符合规范的代码
2. **重复劳动**：格式转换、数据提取、日志分析
3. **初版文档**：README 框架、接口说明
4. **机制解释**：为什么会这样、原理是什么
5. **外部复核**：挑出不实宣称、逻辑漏洞

### 灰色地带（需要协商）

1. **性能调优方向**：AI 提建议 → 人评估风险 → 一起实验
2. **架构重构**：AI 提方案 → 人判断时机（项目尾声 = 不做）
3. **错误修复**：简单 bug AI 直接修 / 复杂 bug 人介入判断

## 失败案例与教训

### 教训 1：不要让 AI"猜"用户意图

**错误**：AI 推理"Flash 95% 必须删 TLS"
**真相**：分区方案变了，实际余量 774KB
**教训**：任何静态数字必须回原始产物核对（时点 + 产物 + 分母）

### 教训 2：不要在坏基线上让 AI 连续优化

**错误**：系统已经多指标异常，AI 连做三组对照都"有数据支撑"
**真相**：归因断了，每步都合理但整体方向错
**教训**：先回 Git 锚点，再逐一击破

### 教训 3：实装与否不能看文档口径

**错误**：AI 读教程觉得"这是可选实现指南" → 判断用户没做
**真相**：用户每条回复都有 `📊 上下文 15%` 这个功能
**教训**：代码才是真相，文档措辞会骗人

### 教训 4：别把"代码里没有"当成"没落地"

**错误**：AI 看固件代码没有某功能 → 判断"没落地"
**真相**：功能在会话层状态（OpenClaw 的记忆），不在任何配置文件
**教训**：智能系统的状态可能在代码之外

## 可复用工作流清单

```
□ 阶段 0: 需求澄清
  □ 用户要什么（描述现象 vs 指定方案）
  □ 成功的判据是什么（手感 / 数据 / 两者）
  □ 风险等级（可逆 / 不可逆）

□ 阶段 1: 拆解与路由
  □ 拆成子任务
  □ 识别跨系统边界
  □ 定义接口契约（人审查）
  □ 分配给合适的 Agent

□ 阶段 2: 并行开发
  □ 各 Agent 独立实现
  □ 单侧验收（编译 / 启动 / 单元测试）
  □ 遇到跨界问题 → 回到人

□ 阶段 3: 集成验收
  □ 真机测试（人工操作）
  □ 观察日志 + 屏幕 + 网络抓包
  □ 对比预注册判据

□ 阶段 4: 外部复核（可选）
  □ 发布前调用独立模型
  □ 给源码不给结论
  □ 逐条回代码验真伪

□ 阶段 5: 归档与记忆
  □ 量化数据进台账
  □ 关键教训进记忆
  □ Git 锚点标记里程碑
```

---

**这套工作流的核心价值**：让人和 AI 各自做擅长的事 — 人负责判断（什么是对的），AI 负责执行（怎么做到）。通过接口契约、分阶段验收、外部复核，形成多层质量保障。
