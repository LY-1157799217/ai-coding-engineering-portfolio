# 人在环多 Agent 协同工作流

## 架构概览

**核心理念**：人负责判断与裁决，AI 负责执行与复核，通过**接口契约**与**分阶段验收**实现协同。

**人工定下的五条方法与边界（本工作流的骨架）**：

1. **判据先于动手** —— 开工前先给判据 / 验证基础，防止事后"自圆其说"
2. **逐一击破** —— 一次只改一个变量，每个改动带自己的预注册判据
3. **多指标异常先回锚点** —— 归因断了就别继续在坏基线上优化
4. **验收分工** —— "好不好用"由用户感受验收；"为什么卡"由量化数据定位
5. **Agent 之间不直连** —— 跨系统信息一律经人工转达，接口契约由人审查

⇒ 下面各节是这五条在具体项目里的展开。

### 协同角色分工

| 角色 | 负责范围 | 典型任务 |
|------|---------|---------|
| **人（主导）** | 架构设计（端-边-云布局）、需求拆解、任务路由、冲突裁决、真机验收 | 定义"什么是对的"、系统边界、最终验收 |
| **Claude Code** | Windows 侧固件开发、嵌入式调试 | ESP32 Arduino 代码、性能分析 |
| **OpenClaw** | Linux 侧服务开发、系统集成 | 树莓派 Python 服务、企微 Bot |
| **Work Buddy** | 低风险辅助任务 | 文档整理、数据提取 |
| **Codex (GPT)** | 独立外部复核 | 发布前审查、缺陷发现 |

## 工作流程

### 阶段 1：需求拆解与任务路由

**输入**：用户需求（如"企微群里发指令控制设备"）

**人的决策**：
1. 拆解为子任务：企微 Bot（Pi 侧）+ HTTP 接口（ESP32 侧）+ MQTT 总线
2. 识别风险等级：企微凭证处理 = 高风险（人工审查）/ 网页按钮 = 低风险（AI 直接做）
3. 路由到合适的 Agent：
   - Pi 侧 Python → OpenClaw（Linux 环境）
   - ESP32 C++ → Claude Code（Windows + Arduino）
   - 两侧接口契约 → 人工定义后双方遵守

### 阶段 2：接口契约与协同边界

**契约内容**（ESP32 ↔ Pi 示例）：
```
GET /api/stock/{symbol}
- 响应体：扁平 JSON，< 4KB
- Connection: close（不用 chunked）
- 失败返回：HTTP 非 200，body 可为空
- 超时：ESP32 侧 2000ms
```

**关键约束**：
- 改动一侧需同步另一侧
- 契约由人审查，AI 不能单方面修改
- 跨系统集成点必须有人工验收

### 阶段 3：分阶段验收

**单侧验收**（各 Agent 独立完成）：
- Claude Code：ESP32 固件编译通过、串口日志正常
- OpenClaw：Python 服务启动、Flask 接口返回 200

**集成验收**（人工主导）：
- ESP32 能否从 Pi 拉到数据
- 企微指令能否到达设备
- **真机测试**：实际设备上操作，观察屏幕变化

**性能验收**（**分工由人工界定**）：
- **验收"好不好用"**（UI / 交互 / 流畅性）⇒ **用户感受是唯一判据**，数据只作参考
- **排查"为什么卡 / 为什么饱和"** ⇒ **高精度量化数据是必需品**（否则连路线都选不对）
- 手感看**尾部延迟**（"切换卡不卡"），不看平均值；数据看 12 小时长跑、堆内存趋势、崩溃计数
- ⇒ 两者**是分工，不是对立**：数据负责定位与选路，感受负责验收

### 阶段 4：冲突裁决

**典型冲突场景**：

1. **AI 建议 A，数据显示 B**
   - 示例：AI 推理"堆碎片是 TLS 导致" → 实测降 TLS 3 倍，堆碎片不变
   - 裁决：**数据优先**，推翻 AI 假设

2. **两个 Agent 的方案冲突**
   - 示例：Claude Code 建议异步化，OpenClaw 建议降频率
   - 裁决：**评估风险与收益**，异步化未测过竞态 → 暂不做

3. **AI 说"已修复"，用户说"还是卡"**
   - ⚠️ **不能默认谁错** —— 两边都是采样，两边都可能读到过期状态。
   - **人工给的判据（三步，顺序不能换）**：
     1. 先确认**两边是否都在读实时状态**（烧的是这版吗 / 页面刷新了吗 / 指标是不是点采样、是不是被截断的分布）
     2. 再确认**两边测的是不是同一个"可感的量"**（卡顿要看尾部，不要看平均）
     3. 过了 ①② 才谈优先级：**UI 验收 → 感受优先；机制排查 → 数据优先**
   - **便宜的操作化**：当"指标说好、手感说坏"时，先做一次**强制同步** —— 两边在**同一时刻、同一状态、同一场景**各取一次样，
     而不是拿旧日志对上次印象（等价于写一个 memory barrier，强制重读）。
   - 人工的原话："**类似于人是没有 volatile 指令的，是不是保证读的最新状态呢？不好说。**"
   - 本 case 实测：AI 三轮都在看平均值（125ms，"很健康"），用户三轮说"还是卡"，而**尾部实际是 1.7~40 秒** ⇒ 这一次确实是**指标选错了**。

## 成本控制与模型分级

### 模型选择策略

| 场景 | 模型 | 原因 |
|------|------|------|
| **主力开发** | Claude (Fable / Opus) | 长上下文、代码能力强 |
| **外部复核** | Codex (GPT) | 独立视角、挑错能力 |
| **批量处理** | DeepSeek / Qwen | 成本低、速度快 |
| **需求理解** | OpenClaw (GPT) | 企微自然语言解析 |

### 实际成本（两个项目周期）

实际成本数据涉及个人消费记录，未在此公开。各模型的使用场景与分级策略已在上表说明。

### 成本优化策略

1. **复用上下文**：同一问题域的连续任务在同一会话
2. **分级处理**：简单任务用轻量模型，复杂推理用顶级模型（按任务类型选用当期最强的那个）
3. **外部复核按需**：发布前才调用 Codex (GPT)，不是每次改动
4. **避免重复工作**：Git 锚点 + 增量修复，不推倒重来

## 关键协同模式

### 模式 1：跨系统协同（Windows ↔ Linux）

**场景**：ESP32（Windows 开发）需要与树莓派（Linux）集成

**协同机制**：
1. **人定义接口契约**：HTTP 路径、JSON 字段、超时策略
2. Claude Code 实现 ESP32 侧 HTTP 客户端
3. OpenClaw 实现 Pi 侧 Flask 服务端
4. **人工集成测试**：两侧代码都完成后，真机验证

**关键点（人工定的架构边界，所有项目通用⭐）**：
- **不让两个 Agent 直接通信** —— 它们各自只面对自己那侧的契约
- 所有跨界面信息**经人工转达**
- 接口变更需人工同步通知两侧

### 模式 2：独立复核（外部模型）

**场景**：发布前确保 README、代码注释、配置示例的准确性

**复核流程**：
1. **给源码不给结论**：让 Codex (GPT) 从头分析
2. **要求指出行号**：避免泛泛而谈
3. **逐条回代码验真伪**：人工核实每一条
4. **多轮收敛**：18 → 9 → 7 → 4 → 4 → 2（累计 44 条）

**发现的典型错误**：
- "所有/全部/N 个都…" → 逐个数一遍（有例外）
- "安全" → 从应用到文件系统到挂载参数每层过一遍
- "一律改成…" → 按值的类型分列反例（宏值不能乱改）
- "会/能/自动" → 从失败分支反推（有 else 吗？）

### 模式 3：测量驱动迭代

**典型案例**：性能优化

1. **先测量建立基线**：12 小时长跑、堆内存趋势
2. **AI 提出假设**："TLS 慢是因为 X"
3. **设计可证伪实验**：改 X，预注册判据
4. **数据验证假设**：
   - 假设成立 → 归档，进入下一个
   - 假设证伪 → 推翻，换方向
5. **人工判定终点**："够用了" / "到边界了"

**关键原则（可复用⭐）**：
- **架构方向可假设，落地必须实测**
- 指标必须匹配用户可感的量（尾部 vs 平均）
- **小样本结论只能当假设，不能当数据**
- **判据先于动手**：实验开跑之前先把判据写下来，否则事后总能找到一套"看起来通过"的说辞

## 人机边界的核心原则

### 人负责的事（AI 不能代替）

1. **最终判断**："好不好用" —— **用户感受是唯一判据**（人工界定的适用范围：主要针对 UI / 交互类；
   非 UI 项目、或"自己没设置好"（没烧对版本 / 页面没刷新）时，**手感同样会读错状态**）
2. **风险决策**：删除 vs 保留、推送 vs 本地、异步化 vs 降频率
3. **优先级排序**：先修 A 还是先修 B
4. **验收标准**：什么叫"修好了"
5. **跨系统集成**：两侧代码都对，接口对不对得上

### AI 负责的事（人不必亲自做）

1. **代码生成**：根据需求写出符合规范的代码
2. **重复劳动**：格式转换、数据提取、日志分析
3. **初版文档**：README 框架、接口说明
4. **机制解释**：为什么会这样、原理是什么
5. **外部复核**：挑出不实宣称、逻辑漏洞

### 灰色地带（需要协商）

1. **性能调优方向**：AI 提建议 → 人评估风险 → 一起实验
2. **架构重构**：AI 提方案 → 人判断时机（项目尾声 = 不做）
3. **错误修复**：简单 bug AI 直接修 / 复杂 bug 人介入判断

## AI 的失误与提炼出的判据（照实记）

> 这一节记的都是 **AI 的判断出错过**、以及事后留下的那条判据 —— **判据才是可复用的部分**。
> 每次都把"AI 当时是怎么想的"写出来：错的不是知识，是**推理方式**。

### 失误 1：拿过时数字推理，得出"必须删 TLS"

**AI 的推理**：Flash 占用 95%，空间不够 ⇒ 必须删掉 TLS
**真相**：95% 是**切分区方案之前**的数字；当前方案实际占用 **62.2%**，余量 774KB
**判据（可复用⭐）**：任何静态数字必须回原始产物核对 —— 记录须含**测量时点 + 原始产物 + 分母 / 配置**三要素

### 失误 2：在坏基线上连续优化（三次，零效果）

**AI 的动作**：系统已多指标异常，仍在其上连做三组对照，**每组都"有数据支撑"**
**真相**：归因断了 —— 每次测量同时混着"这次的改动"和"原本就存在的其他病"，**分不开**
**人工的介入**：主动打断 —— "先回到之前那个流畅的版本（Git 锚点），再逐个修 bug"
**判据（可复用⭐⭐⭐）**：**一旦发现**连续两次以上优化都没有明确改善 → **立刻停下，先去找 / 建锚点**，不要在坏基线上继续挖

### 失误 3：把"文档没写全"当成"功能没做"

**AI 的判断**：读教程觉得"这是可选实现指南" ⇒ 判断用户没做这个功能
**真相**：该功能一直在跑（用户每条回复都带 `📊 上下文 15%`）
**判据**：**代码与实际行为才是真相**，文档措辞会骗人

### 失误 4：把"代码里没有"当成"没落地"

**AI 的判断**：固件代码里没有某功能 ⇒ 判断"没落地"
**真相**：功能在**会话层状态**（OpenClaw 的记忆）里，不在任何配置文件中
**判据（可复用⭐）**：**智能系统的状态可能在代码之外** —— 先问"这个状态该存在哪一层"，再去那一层找

## 可复用工作流清单（所有项目通用⭐）

```
□ 阶段 0: 需求澄清
  □ 用户要什么（描述现象 vs 指定方案）
  □ 成功的判据是什么（手感 / 数据 / 两者）—— **动手前就写下来**
  □ 风险等级（可逆 / 不可逆）

□ 阶段 1: 拆解与路由
  □ 拆成子任务
  □ 识别跨系统边界
  □ 定义接口契约（人审查）
  □ 分配给合适的 Agent

□ 阶段 2: 并行开发
  □ 各 Agent 独立实现
  □ 单侧验收（编译 / 启动 / 单元测试）
  □ 遇到跨界问题 → 回到人

□ 阶段 3: 集成验收
  □ 真机测试（人工操作）
  □ 观察日志 + 屏幕 + 网络抓包
  □ 对比预注册判据

□ 阶段 4: 外部复核（可选）
  □ 发布前调用独立模型
  □ 给源码不给结论
  □ 逐条回代码验真伪

□ 阶段 5: 归档与记忆
  □ 量化数据进台账
  □ 关键教训进记忆
  □ Git 锚点标记里程碑
```

---

**这套工作流的核心价值**：让人和 AI 各自做擅长的事 — 人负责判断（什么是对的），AI 负责执行（怎么做到）。通过接口契约、分阶段验收、外部复核，形成多层质量保障。
